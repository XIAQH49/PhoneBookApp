# v0.6 PC 意图直达导入说明（hdc 意图传参 → APP 复用导入管线）

| 项 | 内容 |
|---|---|
| 版本 | v0.6.1（2026-09-09 收尾：size 自适应分批 + bat 修复 + 本文档） |
| 定位 | **内置名单（v0.5）的替代方案**：名单更新不再打包进 APP、不产生名单文件副本流转 |
| 合规说明 | 按管理要求，名单**不得以内置文件形式传递**（Excel 随包/复制有被认定为数据外泄的风险）。本方案：APP 在外部构建安装一次（**包内无名单**），此后名单经 USB 调试意图逐批"流"进 APP 沙箱数据库，全程无名单文件 artifact、`rawfile/` 保持为空 |

## 1. 链路总览

```
内网 PC：send_list.bat 名单.xlsx
  └─ node sender.ts：XlsxService/CsvService 解析（与 APP 同一套代码）
       └─ 按载荷大小分批（≤8000 字符/批，详见 §4）
            └─ 逐批：hdc shell aa start -b com.example.phonebookapp -a EntryAbility --ps payload <base64(JSON)>
手机 APP：EntryAbility.onCreate（冷）/ onNewWant（热）
  └─ IntentImportService.handleWant：base64→JSON→批次落盘沙箱 filesDir/intent_import/<transferId>/
       └─ 收齐（1..total 连续无缺）→ headers+rows 拼 CSV（CsvService.toCsv）
            └─ ImportService.importFromBytes（与手动导入完全同链路：解析/合并取"或"/入库/元信息）
                 └─ 主页 onPageShow toast「已从内网导入 N 条」并刷新
```

- 批次协议：`{action:'import_rows', transferId, batch, total, headers[], rows[][]}`，base64(UTF-8 JSON) 放单个 `--ps payload` 参数；
- 同一 transferId 收不齐 → toast「接收不完整，请在 PC 端重发」；重跑脚本会刷新 transferId 全量重发，合并语义不丢已打/打通/意向状态；
- 该导入**不写** `builtin_last_hash`，与内置名单相互独立。

## 2. 内网操作步骤（每次名单更新）

前提：内网电脑已拉取本仓库源码（含 `tools/`）、装有 DevEco Studio（自带 node 与 hdc）、手机 USB 连接（`hdc list targets` 可见）且 APP 已用 IDE Run 安装。

1. 把内网导出的最新名单（xlsx 或 csv）放到任意路径；
2. 打开 cmd：`cd /d <仓库>\tools\intent_sender`；
3. 执行：`send_list.bat "D:\path\名单.xlsx"`（缺省取本目录最新 .xlsx；支持透传参数，见 §4）；
4. 观察批次进度 `batch N/M: OK`；全部 OK 后手机主页提示「已从内网导入 N 条」即完成；
5. 若 APP 提示接收不完整：原样重跑本脚本即可（全量重发、合并导入）。

## 3. aa start 语法结论

```
hdc shell aa start -b com.example.phonebookapp -a EntryAbility --ps payload <base64字符串>
```

- `--ps key value` 为 aa 工具字符串参数标准语法；载荷为 base64 标准字符集（A-Za-z0-9+/=），**无 shell 特殊字符**，无需引号转义；
- APP 侧 `want.parameters['payload']` 读取；设备默认 singleton，APP 在前台时回调 `onNewWant`（热路径），未启动时走 `onCreate`（冷路径），两路径共用同一接收逻辑；
- ✅ **真机实测结论（2026-09-09，5XM0225B10002581）**：上述语法可用，`--max-chars 8000` 载荷 146/146 批全部送达并导入成功（真实名单 20 列 2347 行），`aa` 成功输出为 `start ability successfully.`。

## 4. 分批策略与实测数据（v0.6.1 size 自适应）

- **为什么改为按大小分批**：宽表（真实名单 20 列）与窄表（样例 6 列）单行字节差约 4 倍；固定 50 行/批在真实名单上产生 **23KB+** 单 intent 参数，逼近 Windows 命令行 32K 上限且设备侧风险未知；
- 策略：逐行累加，精确编码后超 `--max-chars`（默认 **8000** 字符）即切批，同时受 `--batch` 行数上限（默认 50）约束；单行超长告警并单独成批；
- 调优：`send_list.bat 名单.xlsx --max-chars 4000`（真机若报参数过长/丢批时调小）；
- 实测（本机 dry run）：

| 数据 | 列数 | 行数 | 批数 | 单批载荷 |
|---|---|---|---|---|
| 样例 26 行 | 6 | 26 | 1 | 2380 字符 |
| 样例 2000 行 | 8 | 2000 | 40（行数上限先触发） | ~5.5~5.7K 字符 |
| 真实名单备份 20260831 | 20 | 2347 | 146（大小上限先触发，~15~17 行/批） | ~7.5~7.6K 字符 |

- 速率估算：每批一次 `aa start`（约 0.5~1s），2347 行真实名单 ≈ 2~3 分钟传完；各上限参考：Windows CreateProcess 32K 字符、Binder 事务 1MB，默认 8K 留有充足余量。

## 5. 故障排查

| 现象 | 排查 |
|---|---|
| `hdc 不可用或未连接设备` | USB 线/调试授权；`hdc list targets` 应见设备；必要时 `hdc kill -r` |
| 批次 `FAIL -> ...` | 看报错文本：参数过长 → `--max-chars 4000` 重试；设备离线 → 重插 USB |
| APP 提示「接收不完整」 | 某批未达：原样重跑脚本（全量重发）；多次不完整 → 调小 `--max-chars` |
| APP 无提示 | 打开 APP 停留在主页（热路径 onNewWant 会即时接收；冷路径下次启动导入）；查 hilog `PhoneBook`/`IntentImportService` |
| 导入行数与文件不符 | 查 hilog `merge stats`（parsed/skippedEmpty/inserts/updates/removed），对照 docs/08 v0.5.3 同键行语义 |
| bat 运行出现 `'_list.bat' 不是内部或外部命令` 类乱码报错 | bat 被保存成了 UTF-8/LF：cmd 按 GBK 解码导致解析错乱。**该文件必须保持 ANSI(GBK)+CRLF**（2026-09-09 已修复为此格式，编辑器另存时注意） |

## 7. 与内置名单（v0.5）的关系

- `rawfile/` **保持为空**（仅 README.txt），不再放入任何名单文件；构建产物 HAP 不含名单；
- 内置名单代码保留（空目录时为无操作），按合规要求停用；一键导出原始文件（FR-12）因同样原因同步停用（无内置文件可导）；
- 旧流程（名单→rawfile→构建→Run）作废，名单更新统一走本文档流程。
